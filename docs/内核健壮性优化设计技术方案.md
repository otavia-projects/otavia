# Otavia 内核健壮性优化设计技术方案

## 0. 编程模型前提(本文所有论证的基础)

在评审与设计前,先固化对 Otavia 编程模型与运行时的几条关键事实。所有后续设计都建立在这些事实之上,任何与之冲突的"优化"都是错误的。

### 0.1 一切都是异步,Stack 是状态机

用户业务**永远不会同步阻塞**。用户写的所有 `resumeAsk` / `resumeNotice` / `resumeChannelStack` 都是 stack 状态机的**单步推进**:

- 在一步内可能发起 `address.ask(...)` / `channel.ask(...)`,但这两个 ask **本身只是把 envelope 推到目标 mailbox(actor 间)或挂到 channel 的 `pendingFutures`(channel 间),立即返回 `Future`**
- 用户随后调用 `stack.suspend(state)` 返回 `StackYield.SUSPEND`,本步结束
- Stack 被挂起,等待 `MessagePromise`/`ChannelPromise` 完成
- 对方 reply 或 channel inbound 响应到达时,promise 被 setSuccess,触发 stack 重新进入 dispatch,**下一次** `resume*` 被调用,继续状态机的下一步

**因此根本不存在"业务回调长耗时"或"业务同步阻塞"** —— 那是 actor 框架的反模式。任何这种现象都是**用户错用框架**,不是内核应当兜底的设计目标。

### 0.2 同步调用栈深度恒定

观察 ChannelFuture 的"同步重入"链路:

```
NioHandler.processSelectedKey
 → NioUnsafeSocketChannel.doReadNow0
 → AbstractChannel.handleChannelReadBuffer
 → pipeline.fireChannelRead (decoder 把 buffer 解出消息)
 → AbstractChannel.onInboundMessage
 → inflightFutures.pop().setSuccess(msg)
 → ChannelFuture.completed
 → actor.receiveFuture
 → handlePromiseCompleted
 → dispatchAskStack / dispatchChannelStack
 → resumeAsk / resumeChannelStack (用户代码,推进状态机一步)
 → 用户代码可能再 channel.ask(...) → pendingFutures.append (O(1) 异步)
 → stack.suspend(...) 返回 SUSPEND
 → switchState 把 stack 挂起
(回到 onInboundMessage)
 → processPendingFutures (把刚追加的 ask write 到 socket buffer)
```

**栈深度是恒定常数**(约 10 层),与同时完成的 promise 数无关。decoder 在循环里把一个 buffer 解出 N 条消息,每条触发一次 `onInboundMessage`,这是**循环**而非递归。

所以"递归栈溢出"风险**不存在**。任何以"递归打平"为出发点的方案都是无效的,且会引入额外延迟、破坏数据热度。

### 0.3 actor 间 ask 完全跨 mailbox 异步

`address.ask` → `house.putAsk(envelope)` → 入对方 actor 的 `askMailbox`,**永不在调用方调用栈内同步完成**。reply 也是反过来通过 `replyMailbox` 异步回流。actor 间通信的同步路径根本不存在。

### 0.4 ChannelPromise 无竞争

ChannelPromise 的完整生命周期都在同一个 ActorThread 上:

1. **创建 + 入队**: `channel.ask(...)` 在 `resumeAsk` / `resumeChannelStack` 中调用 → ActorThread 上执行
2. **响应完成**: IO 阶段 `onInboundMessage` → `inflightFutures.tryRemove(id)` → `setSuccess` → 同一 ActorThread
3. **超时完成**(§2 实施后): eventMailbox dispatch → `tryRemove(id)` → `setFailure` → 同一 ActorThread
4. **关闭失败**: `close` → `failedFutures` 遍历 inflightFutures → 同一 ActorThread

单线程 + `QueueMap.tryRemove` 先移除再完成,保证同一 promise 不会被第二次找到。后到的那个 `tryRemove` 返回 null,直接跳过。因此 ChannelPromise 不存在 double-complete 的竞争问题。

### 0.5 Mount 异常已兜底

`AbstractActor.mount()` 已经 try/catch 了用户钩子 `afterMount`:

```scala
final private[core] def mount(): Unit = try {
    this.afterMount()
} catch {
    case t: Throwable => logger.error("afterMount error with", t)
}
```

`ActorHouse.doMount` 调 `dweller.mount()` 时异常不会向上穿透,事件循环不会因 mount 失败而崩溃。

### 0.6 配置校验已存在

`OtaviaConfigBuilder` 中 `SchedulerConfigBuilder.build()` 已有完整的防御性校验(fallback 到默认值):

```scala
val ioRatio =
    if (rawIoRatio <= 0 || rawIoRatio > 100) {
        Report.report(s"cc.otavia.actor.io.ratio can't set $rawIoRatio, ...")
        50
    } else rawIoRatio
```

通过正常配置路径(builder / system property)不会触发 `computeDeadline` 的除零异常。

### 0.7 真正的运行时风险

基于以上事实,内核健壮性的真正风险在两个方面:

1. **生命周期**:停机(shutdown)资源释放未实现完整契约
2. **功能缺失**:Channel ask 无超时机制,与 actor ask 不对称

---

## 一、Shutdown 资源释放

### 1.1 现状

[`ActorThread.run()`](../core/src/cc/otavia/core/system/ActorThread.scala:197) 主循环退出后**没有任何清理**:

```scala
override def run(): Unit = {
    prepared()
    ...
    while (!confirmShutdown()) { /* ... */ }
    // 退出后什么都不做
}
```

[`ActorThread.shutdown()`](../core/src/cc/otavia/core/system/ActorThread.scala:188) 只置 `shuttingDown = true` + `wakeup()`:

```scala
private[core] def shutdown(): Unit = {
    shuttingDown = true
    ioHandler.wakeup()
}
```

退出后:
- `Selector` 不被 `destroy()` 关闭
- 所有 channel 不被 close,远端收到 RST
- 对象池借出未还的 Stack/Promise/Envelope 永久泄漏

### 1.2 触发场景

| 场景 | 影响 |
|------|------|
| 嵌入式应用反复启停 ActorSystem | 每次泄漏 Selector + fd + 若干对象池对象,几百次 OOM/fd 耗尽 |
| 单元测试套件 | 上千测试用例后内存爆 |
| 生产优雅停机 | 远端看到 RST 而非 FIN |

### 1.3 设计

在 `run()` 退出后增加 finally 块执行清理:

```scala
override def run(): Unit = {
    prepared()
    try {
        while (!confirmShutdown()) { /* 主循环 */ }
    } finally {
        doShutdownCleanup()
    }
}

private def doShutdownCleanup(): Unit = {
    // 1. 关闭所有 channel(发 FIN,远端正常感知)
    manager.allHouses.foreach { house =>
        house.actor match {
            case ca: ChannelsActor[?] => ca.activeChannels.foreach { ch =>
                try ch.close() catch { case t: Throwable => logger.warn("close channel", t) }
            }
            case _ =>
        }
    }

    // 2. 关闭 IO handler(释放 selector 与 OS 资源)
    try ioHandler.destroy() catch { case t: Throwable => logger.warn("destroy IoHandler", t) }
}
```

### 1.4 性能与延迟

- 稳态:零影响,只在停机时执行
- 清理顺序:先关 channel(发 FIN)再 destroy selector(释放 fd)

## 二、activeChannels 完整化

### 2.1 现状

[`ChannelsActor.activeChannels`](../core/src/cc/otavia/core/actor/ChannelsActor.scala:48) 是一个 `mutable.HashSet`,登记点:

- 客户端路径:`createChannelAndInit` 内 `activeChannels.add(channel)` ✅
- 服务端路径:`AcceptedWorkerActor.handleAccepted` **没有登记** ❌

### 2.2 问题

服务端 worker actor 的所有 child channel 都不在 `activeChannels` 内,导致:

- shutdown 时这些 channel 不会被主动 close(配合 §1 的 shutdown 清理),远端看到 RST 而非 FIN
- 监控接口报告的"当前连接数"是 0,与真实 OS 状态不一致

### 2.3 设计

`AcceptedWorkerActor.handleAccepted` 在 `register` 成功后,内核默认登记:

```scala
case registerState: ChannelFutureState =>
    val future = registerState.future
    if (future.isSuccess) {
        activeChannels.add(future.channel.asInstanceOf[Channel])  // ← 内核默认登记
        afterAccepted(future.channel)
        stack.`return`(UnitReply())
    } else stack.`throw`(future.causeUnsafe)
```

`afterChannelClosed` 钩子内已有的 `activeChannels.remove(e.channel)` 保持不变,出入对称。

### 2.4 性能与延迟

- 每次 `handleAccepted` 多一次 HashSet.add — O(1),纳秒级
- 关停路径 O(active channels) 一次性遍历,不影响稳态

## 三、Channel ask 超时

### 3.1 现状

- [`PhysicalAddress.ask(ask, future, timeout)`](../core/src/cc/otavia/core/address/PhysicalAddress.scala:57) 支持 timeout,通过 `timer.registerAskTimeout` 注册
- [`AbstractChannel.ask(value, future)`](../core/src/cc/otavia/core/channel/AbstractChannel.scala:259) **没有 timeout 重载**,channel ask 永远不超时

### 3.2 问题

- 远端服务挂死、网络半连接、对端代码 bug 不回包等场景下,`ChannelFuture` 永远停在 `inflightFutures` 中
- 用户层无法通过 `channel.ask(value, future, timeout)` 控制超时,只能通过应用层定时器自己监督,**违反框架的契约一致性**

### 3.3 设计

#### 3.3.1 ChannelAddress 增加 timeout 重载

```scala
trait ChannelAddress {
    def ask(value: AnyRef, future: ChannelFuture): ChannelFuture
    // 新增
    def ask(value: AnyRef, future: ChannelFuture, timeout: Long): ChannelFuture
}
```

`AbstractChannel` 实现:

```scala
override def ask(value: AnyRef, future: ChannelFuture, timeout: Long): ChannelFuture = {
    ask(value, future)
    val promise = future.promise
    val id = system.timer.registerChannelAskTimeout(
        TimeoutTrigger.DelayTime(timeout),
        actor.self,
        this,
        promise.messageId
    )
    promise.setTimeoutId(id)
    future
}
```

#### 3.3.2 超时事件处理

新增 `ChannelAskTimeoutEvent(channel, messageId)`,投到 actor 的 eventMailbox。`ChannelsActor` 增加分支:

```scala
case e: ChannelAskTimeoutEvent =>
    val ch = e.channel.asInstanceOf[AbstractChannel]
    // 从 inflightFutures 中移除 promise(避免响应再到达时错配)
    val promise = ch.inflightFutures.tryRemove(e.messageId)
    if (promise != null && !promise.isDone) {
        promise.setFailure(new TimeoutException(...))
    }
```

#### 3.3.3 实现路径

新增 `ChannelAskTimeoutTask`(参照已有的 `AskTimeoutTask`)和 `ChannelAskTimeoutEvent`(参照 `AskTimeoutEvent`),在 Timer 中增加 `registerChannelAskTimeout` 方法。已有的 `QueueMap.tryRemove` 方法可直接用于从 `inflightFutures` 中按 messageId 移除 promise。

### 3.4 性能与延迟

- 不开启 timeout 时:**零开销**(只是多个未调用的方法)
- 开启 timeout 时:每个 ask 多一次 timer 注册(O(log n) 时间堆插入),与 actor 间 ask 一致,无新开销
- 超时事件投递走标准 eventMailbox 路径,不影响热路径

## 四、落地路线图

### 5.1 优先级矩阵

| 项目 | 类型 | 优先级 | 复杂度 | 风险 |
|------|------|-------|-------|------|
| §1 Shutdown 资源释放 | bug 修复 | P0 | 中 | 涉及 ActorThread 主循环 |
| §2 activeChannels 完整化 | bug 修复 | P1 | 极低 | 一行 add |
| §3 Channel ask timeout | 功能补全 | P1 | 中 | 需要扩展 Timer 接口 |

### 4.2 推荐实施顺序

**第一批(P0 + P1 低复杂度)**:
1. §2 activeChannels 完整化(一行代码,§1 的前提)
2. §1 Shutdown 资源释放

**第二批(P1 功能补全)**:
3. §3 Channel ask timeout

### 4.3 测试策略

| 类型 | 测试手段 |
|------|---------|
| Shutdown 清理 | 1000 次 start/stop 循环 + 监控 fd 数 + selector 数 |
| activeChannels | 服务端 accept 连接后验证 activeChannels 包含 child channel,shutdown 后验证收到 FIN |
| Channel ask timeout | 故意阻塞响应,验证 timeout 触发、inflightFutures 中 promise 被移除、超时后迟到的响应不会错配 |

### 4.4 兼容性

- **API 兼容**:`ChannelAddress.ask` 仅新增 timeout 重载,不破坏现有签名
- **行为兼容**:shutdown 清理是新增行为,不影响稳态;activeChannels 追踪是内部数据结构补全,不影响用户 API
